# Assignment(과제) - 과제 CRUD 슬라이스 설계

> 상태: 초안 (PM 검토 대기)
> 역할: 이 슬라이스의 범위와 결정 기록 - 확정 후에는 거의 갱신하지 않으며, 결정은 BE PR 본문에 옮긴다
> 기준 규약: [guide/design.md](../guide/design.md) 3절·4절 - 이 문서는 그 규약에 추가되는 결정만 기록
> 스키마 원본: [db/schema.md](../db/schema.md) - assignments 테이블·삭제 정책·지각 계산 규칙은 그쪽이 확정본
> 문서 구성: [api.md](api.md)(구현 계약) · [test.md](test.md)(테스트 계획) · [fe.md](fe.md)(FE 연동)

## 1. 범위

- 과제 CRUD API 5개 (`assignment` 패키지 신설) - 명세는 [api.md](api.md)
- 제출(Submission)·현황판·상태 계산(미제출/제출/제출(추가)/지각)은 다음 슬라이스 - Submission 엔티티가 없는 상태에서 앞당겨 설계하면 추측이 됨
- 이 슬라이스로 FE 과제 목록·상세 화면의 목데이터를 실제 API로 교체 가능 - 매핑은 [fe.md](fe.md)

## 2. 결정

1. **슬라이스 범위 = CRUD만** - 상태 계산·submissionCount·삭제 시 "제출물 N건 삭제" 경고 데이터는 제출 슬라이스로 이월. 이 슬라이스의 DELETE는 과제 행만 삭제 - 제출 슬라이스 이후에는 FK(RESTRICT)가 삭제 순서 누락을 에러로 알려 주는 안전망이 되고, 연쇄 삭제(파일 → submissions → assignment)는 그때 서비스에 구현 (schema.md 4절)
2. **목록 정렬 = 차시 오름차순(차시 없음 마지막) → 등록순** *(2026-08-25 갱신 - 최초 결정은 createdAt desc)* - 화면 그룹핑 기준이 차시. P1은 페이징이 없어 FE가 전체 목록을 받으므로 D-day순 등 재정렬은 FE 자유. "서버 판정값 그대로" 규칙은 마감·상태 배지에 대한 것이지 정렬 아님
3. **과거 dueAt 허용** - 생성·수정 모두 서버는 차단하지 않음. 즉시 마감·마감 단축은 운영 판단이고, 막으면 "마감 수정 → 지각 재계산" 규칙과 어긋나는 예외가 생김. 실수 방지는 FE 확인 UI 몫
4. **description 최대 10000자** - TEXT지만 무제한 입력 방지. 분반 description(2000자)보다 긴 이유: 과제 본문은 문제 설명·링크가 들어가는 실질 콘텐츠
5. **응답 DTO는 `AssignmentResponse` 하나** - viewer 의존 필드가 아직 없어 Assembler 불필요, `from(entity)`로 충분. 제출 슬라이스에서 상태 필드 추가 시 Detail 분리 여부 재검토 (guide 8절-8 패턴)
6. **차시 = `sessionNo` 선택 정수 열 (2026-08-25)** - 운영진 자유 입력(중복·건너뜀 허용), 차시 밖 과제는 NULL. 엔티티로 만들지 않는 이유: 차시 고유 속성(날짜·제목)이 아직 없음 - 속성이 생기는 출석부(P2) 도입 때 Session 엔티티 승격 재검토 (schema.md 결정 6)
